# 编排子代理

Octogent 用子终端把工作拆成并行流。

如果你是从 shell 派活的那一方——人，或者本身不是 Octogent 终端的 AI 协调者——先看[协调者工作法](getting-work-done.md#协调者工作法派发--等待--读回答--追问--审阅--收尾)：派发、`terminal wait`、`terminal result`、通过 channel 追问、审阅、收尾。本页讲的是底下的父子终端机制。

## 生成的工作方式

子代理就是一条设置了 `parentTerminalId` 的普通终端记录。这层关系保存在终端注册表并显示在 UI 中；子终端仍然拥有自己的终端 ID、生命周期状态、转录、工作区模式和可选的工作树。

Deck 通过解析提示词模板，从待办项创建子代理。提示词会拿到触手名称、触手 ID、`.octogent/tentacles/<tentacle-id>/` 路径、待办文本、终端 ID、API 端口、工作区指引，以及存在父终端时的父终端 ID。

## 何时使用子代理

在以下情况使用子代理：

- 任务足够独立，可以并行推进
- 父代理能划出干净的范围
- 每个任务对应一个触手或一条待办
- 预期的文件重叠很低，或者可以使用工作树模式

当工作彼此纠缠、代理会互相覆盖时，不要使用。

## 推荐工作流

1. 创建或选择一个触手
2. 编写或完善 `CONTEXT.md`
3. 把工作拆成 `todo.md` 里的复选框项
4. 从这些待办项生成工作终端
5. 在父终端里评审结果
6. 工作代理之间需要协调时使用通道消息
7. 只有在评审结果之后才更新 `todo.md`

## 共享模式与工作树模式

使用 `shared`（共享）当：

- 任务以读为主
- 改动很小
- 你想要最快的启动

使用 `worktree`（工作树）当：

- 任务会触碰重叠的文件
- 你想要干净的 git 隔离
- 预期有较大的代码改动

共享模式下，所有工作代理都在主工作区运行，并被告知不要提交。这更快，但依赖谨慎的范围划分与评审。

工作树模式下，每个工作代理在 `.octogent/worktrees/<worker-terminal-id>/` 下获得名为 `octogent/<worker-terminal-id>` 的分支，并被告知提交自己的工作。父协调者负责合并分支、运行测试和更新触手状态。

## 父协调者的行为

当一个集群的目标项超过一个时，Octogent 会创建形如 `<tentacle-id>-swarm-parent` 的父终端。父提示词包含：

- 工作终端 ID 与指派的待办索引列表
- 创建每个工作终端的命令
- 使用 `octogent channel send` 的通信说明
- 共享模式或工作树模式下的完成策略
- 最终要求：评审、测试并更新触手文档/待办

父代理刻意不做成一个魔法调度器。它是一个带明确指令、拥有可见终端的代理会话。这让编排既可检视也可打断。

## 工作代理上限与身份

每个父代理最多可有 9 个子终端。如果集群的未完成待办超过这个数量，Octogent 按待办顺序作为优先级顺序，把溢出的部分延后。

工作终端 ID 由触手 ID 和待办索引推导。这让重复检测变得简单：Octogent 会拒绝为同一项模式启动第二个活跃的求解或集群。

## 限制

- PTY 会话不会在 API 重启后存活
- 通道消息只存在于内存
- 委派质量取决于 `CONTEXT.md` 与 `todo.md` 的质量
- 共享模式的工作代理仍可能在文件上相撞，因为共享模式不是 git 隔离
- 工作树模式的工作代理仍需要人工或父代理的合并步骤，其工作才会进入基础分支
